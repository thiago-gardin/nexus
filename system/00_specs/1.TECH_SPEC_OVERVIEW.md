# NEXUS — Technical Specification Overview
## Version 0.3

## 1. Purpose
This document defines the macro-technical frame of the Nexus and indexes the component specifications that operationalize it.

Nexus is a cognitive-operational infrastructure in which:
- a **local executable core** preserves identity, relational integrity, history, mutation, and auditability;
- a **materialization regime** publishes stable, legible, versionable semantic artifacts;
- **human and agent surfaces** operate over the same institutional object space under explicit governance.

## 2. Scope
This overview specifies:
- system-wide architectural principles;
- precedence between executable truth and publishable truth;
- macro-regimes of the system;
- the decomposition of the full technical specification into component documents.

## 3. Out of Scope
This overview does not specify in detail:
- database schema implementation;
- per-component UI behavior;
- API payload examples beyond naming and boundaries;
- build sequencing at task level.

## 4. Normative Principles
### P1 — Executable Precedence
The local database-backed core is the source of executable truth.

### P2 — Publishable Materialization
Entities, relations, events, decisions, payloads, and projections must be externalizable as stable semantic artifacts.

### P3 — Functional Symmetry Under Governance
Humans and agents must share practical capacity of observation, interrogation, proposal, review, and decision, without unrestricted parity of mutation privilege.

### P4 — Domain-Scoped Semantics
All ingestion, typing, reconciliation, and stabilization occur under domain context.

### P5 — Structure / Payload / Projection Distinction
The system must distinguish:
- executable structure;
- referenced canonical payloads;
- publishable projections.

### P6 — Controlled Reentry
Changes originating in materialized artifacts must reenter the executable core only through governed proposal, reconciliation, or authorized mutation.

### P7 — Remote Readability
While stable remote runtime access is not institutionally reliable, remote agents must operate through materialized treefolder-based semantic artifacts and structured proposal channels.

## 5. System Regimes
```text
[ SOURCES ]
      ↓
[ INGESTION AND TYPING ]
      ↓
[ LOCAL EXECUTABLE CORE ]
      ↕
[ MATERIALIZATION REGIME ]
      ↕
[ OPERATION SURFACES ]
```

### 5.1 Local Executable Core
Responsible for:
- identity;
- relational integrity;
- versioning;
- mutation;
- reconciliation;
- decision queues;
- audit trail.

### 5.2 Materialization Regime
Responsible for:
- payload storage references;
- semantic views;
- projections;
- snapshots;
- remote-readable treefolder publication;
- controlled reentry.

### 5.3 Operation Surfaces
Two principal surfaces:
- **human cockpit**;
- **agent surface / MCP**.

## 6. High-Level Technical Decisions
### D1 — DB-first, file-published, payload-referenced
Files do not replace the executable core. Long payloads do not need to live as sovereign columns.

### D2 — Materialization is Operational
Materialization is not cosmetic export. It is a governed regime of publication, reading, circulation, and reentry.

### D3 — Remote Agents Are Read-Mostly / Proposal-Only
Remote agents read projections and submit structured proposals. They do not mutate the executable core directly.

### D4 — Cockpit Is a First-Class Surface
The cockpit is not decorative UI. It is the principal human operational surface of the system.

### D5 — Treefolder Is an Official Remote Interface
The remote treefolder is a formal publication surface, not an incidental export.

## 9. Consistency Rules Across All Child Specs
1. Child specs must not redefine global principles.
2. Child specs may refine, but not invert, executable precedence.
3. Child specs must distinguish mandatory requirements from future directions where relevant.
4. Child specs must preserve the separation between core, materialization, and surfaces.
5. Child specs must remain interoperable by stable object identities.
